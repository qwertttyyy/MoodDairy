## Вывод по задержке запуска

Когда виден текст «Подготавливаем приложение…», основные JS, React и AppPage уже исполняются. В этом состоянии AuthProvider последовательно ждёт config → me → unwrap-key, если ключ нужно восстанавливать. Только затем монтируется лента, подгружается её lazy chunk и запрашивается grouped. Если sessionStorage сохранился, unwrap-key пропускается.

PBKDF2 на 600 000 итераций выполняется при входе/регистрации. Обычный восстановленный запуск использует AES-GCM unwrap; снижать PBKDF2 ради этого сценария бессмысленно и опасно для совместимости.

Контролируемый эксперимент Chromium, production build, новый browser context, API-заглушки: при искусственной задержке 400 мс на ответ цепочка с unwrap дала около 2,6 с до ленты, без unwrap — около 2,1 с. Абсолютные значения включают стенд и работу браузера; эксперимент подтверждает последовательность ожиданий, но не предсказывает точное ускорение iPhone.

P3 — последующая оптимизация/рефакторинг. «Воспроизведено» означает отдельный эксперимент; «по коду» — установленное поведение или риск без проверки на production.

### 1. [P1, frontend/performance] Последовательный bootstrap задерживает запуск

Где: [AuthProvider.tsx:63](/home/mikhail/PychramProjects/MoodDairy/frontend/src/features/auth/AuthProvider.tsx:63), [AppPage.tsx:20](/home/mikhail/PychramProjects/MoodDairy/frontend/src/pages/AppPage/AppPage.tsx:20). Воспроизведено.

До готовности ленты выполняются 3–4 последовательных сетевых этапа. Даже быстрый backend не устраняет RTT каждого этапа. Lazy chunk ленты также обнаруживается поздно.

**Рекомендуется:** единый bootstrap endpoint: конфигурация, пользователь, параметры/версия сессии и wrapping key только для проверенной сессии. Устанавливать CSRF cookie, отдавать no-store. Показывать оболочку рано, загружать код ленты параллельно bootstrap; дневниковые данные открывать после проверки сессии и ключа.

**Альтернатива:** параллельно получать config и me, убрать отдельный запрос unwrap из критического пути через ответ me. Это меньше меняет API, но сохраняет часть накладных расходов.

Проверка: User Timing для этапов + 20 холодных запусков на iPhone с p50/p95 и контролем числа последовательных запросов.

### 2. [P1, UI/themes] Уменьшение прозрачности выключает blur, но оставляет прозрачную заливку

Где: [base.css:205](/home/mikhail/PychramProjects/MoodDairy/frontend/src/shared/styles/base.css:205), [shell.css](/home/mikhail/PychramProjects/MoodDairy/frontend/src/shared/styles/shell.css), [base.css:513](/home/mikhail/PychramProjects/MoodDairy/frontend/src/shared/styles/base.css:513). Подтверждено правилами каскада и проверкой computed styles.

Корневой --lg-bg переопределяется локальными --lg-bg у tab-bar. Important на родительской custom property не запрещает дочернему элементу задать собственное значение. У btn-icon-glass фон вообще задан непосредственно rgba. Blur убирается, фон остаётся полупрозрачным — содержимое под панелью становится различимее. Ошибка касается обеих тем. Модалка имеет отдельную solid-поправку и ведёт себя иначе. Ручная настройка и системный media query также реализованы неодинаково.

**Рекомендуется:** единые токены материалов и явные конечные правила на самих поверхностях: solid background + отсутствие blur для reduced-режима; отдельно учесть tab-bar, info buttons и toast. Объединить ручной/системный режим в вычисляемую настройку, применять её до первого paint.

**Альтернатива:** точечные CSS overrides для каждого элемента. Быстрее, но оставляет риск повторения при добавлении новой поверхности.

Проверка: light/dark × reduced on/off, computed alpha = 1 у поверхностей, переключение и перезапуск. Снимки находятся в evidence/themes.

### 3. [P1, frontend/data] Ключ шифрования не привязан к аккаунту

Где: [AuthProvider.tsx:195](/home/mikhail/PychramProjects/MoodDairy/frontend/src/features/auth/AuthProvider.tsx:195), [crypto.ts](/home/mikhail/PychramProjects/MoodDairy/frontend/src/shared/crypto/crypto.ts), [api.ts:49](/home/mikhail/PychramProjects/MoodDairy/frontend/src/features/entries/api.ts:49). Воспроизведено браузером и реальным AES-GCM.

Серверная cookie общая для вкладок, sessionStorage отдельный. После смены аккаунта в другой вкладке me может вернуть B, а hasKey принять ключ A. В эксперименте новая запись аккаунта B успешно сохранилась под ключом A и не расшифровалась ключом B. Query keys также не содержат user ID.

**Рекомендуется:** хранить идентификатор владельца и версию ключа, проверять key-check до чтения/записи, включить user ID в query keys, синхронизировать logout/switch через BroadcastChannel. При несовпадении блокировать запись и запрашивать разблокировку.

**Альтернатива:** при каждом обнаруженном изменении сессии полностью сбрасывать клиент и требовать новый вход. Проще, но UX хуже. Одного префикса storage без проверки ключа недостаточно.

### 4. [P1, auth/data] API обрезает пробелы пароля, клиент — нет

Где: [accounts/serializers.py:22](/home/mikhail/PychramProjects/MoodDairy/backend/accounts/serializers.py:22), [accounts/serializers.py:76](/home/mikhail/PychramProjects/MoodDairy/backend/accounts/serializers.py:76), [AuthProvider.tsx](/home/mikhail/PychramProjects/MoodDairy/frontend/src/features/auth/AuthProvider.tsx). Воспроизведено.

DRF CharField по умолчанию trim_whitespace=True. Пароль с пробелами и без них одинаков для API, но даёт разные PBKDF2-ключи. Вход проходит успешно, данные могут перестать читаться; возможна запись под несколькими ключами.

**Рекомендуется:** единый точный контракт пароля с trim_whitespace=False для новых аккаунтов, версионирование и контролируемая совместимость старых аккаунтов, key-check перед открытием дневника. Существующие ключи нельзя автоматически заменить: часть пользователей уже могла шифровать паролем с пробелами.

**Альтернатива:** временно запретить краевые пробелы при новой регистрации. Это предотвращает новые случаи, но не исправляет старые аккаунты.

### 5. [P1, crypto/architecture] Смена пароля разрывает доступ к старым данным

Где: [crypto.ts:57](/home/mikhail/PychramProjects/MoodDairy/frontend/src/shared/crypto/crypto.ts:57), [accounts/admin.py:16](/home/mikhail/PychramProjects/MoodDairy/backend/accounts/admin.py:16). Сценарий установлен по коду.

Ключ данных напрямую выводится из пароля. Стандартная смена/сброс пароля Django, включая админку, не переворачивает шифрование записей. Следующий вход выводит другой ключ, история остаётся зашифрованной старым.

**Рекомендуется:** случайный data encryption key, обёрнутый password-derived key; при смене пароля переоборачивать DEK. Для legacy-формата нужна миграция после успешной разблокировки и продуманное восстановление.

**Альтернатива:** до внедрения такого протокола запретить обычный reset для зашифрованных аккаунтов и предоставить специальную операцию со старым паролем. Смена только серверного хеша не восстанавливает данные.

### 6. [P1, frontend/reliability] Временная ошибка unwrap завершает рабочую сессию

Где: [AuthProvider.tsx:201](/home/mikhail/PychramProjects/MoodDairy/frontend/src/features/auth/AuthProvider.tsx:201). Воспроизведено: 503 от unwrap → POST logout → «Не удалось запустить приложение».

NetworkError, timeout, серверная 503 и действительно повреждённый ключ попадают в один catch. Вместо повторяемого временного сбоя пользователь получает logout и invalid-config. Дополнительный logout сам может ждать 20 с.

**Рекомендуется:** разделить транспортные ошибки, истёкшую сессию и неверный ключ; при временном сбое сохранять сессию и предлагать повтор этапа. Ввести общий deadline bootstrap: сейчас 12 с относятся только к config, остальные запросы имеют отдельные 20 с.

**Альтернатива:** короткий ограниченный повтор unwrap перед общим экраном ошибки, без уничтожения серверной сессии.

### 7. [P2, frontend/performance] Сохранение ждёт перезагрузки всех страниц ленты

Где: [entries/api.ts](/home/mikhail/PychramProjects/MoodDairy/frontend/src/features/entries/api.ts), [EntryModal.tsx:192](/home/mikhail/PychramProjects/MoodDairy/frontend/src/features/entries/EntryModal.tsx:192). Воспроизведено.

onSuccess возвращает Promise invalidateQueries. Infinite Query последовательно перечитывает загруженные страницы, mutateAsync ждёт их, форма остаётся в «Сохраняем…» после успешной записи в БД. На 5 страницах × 150 мс эксперимент дал 754 мс дополнительного ожидания.

**Рекомендуется:** использовать возвращённую запись для обновления локального кеша; завершать мутацию после подтверждённой записи. Фоновая инвалидация — только нужных представлений; при изменении даты корректно обновлять группы/курсор.

**Альтернатива:** после изменения сбрасывать ленту до первой страницы и обновлять её в фоне, явно сохраняя или восстанавливая позицию пользователя.

### 8. [P1, backend/data] Запись и её теги сохраняются неатомарно

Где: [entries/views.py:52](/home/mikhail/PychramProjects/MoodDairy/backend/entries/views.py:52), [entries/views.py:144](/home/mikhail/PychramProjects/MoodDairy/backend/entries/views.py:144). Воспроизведено fault injection в сохранение M2M: API ответил 400, число MoodEntry выросло с 1 до 2.

Serializer сначала сохраняет MoodEntry, затем связи. Ошибка связей оставляет частично выполненную операцию. Инвалидация кеша после save не вызывается; повтор пользователем может создать дубль. Все IntegrityError дополнительно превращаются общим handler в validation_error, скрывая часть программных ошибок.

**Рекомендуется:** отдельная транзакционная команда create/update entry с изменением тегов внутри atomic, инвалидация через on_commit. Ожидаемые конфликты переводить в конкретную ошибку за пределами транзакции; неожиданные логировать как серверный сбой.

**Альтернатива:** atomic на create/update view. Минимальное исправление, но ответственность записи остаётся размазанной между view и serializer.

### 9. [P1, backend/cache] При исчезновении версии Redis возвращаются старые ответы

Где: [core/cache.py:37](/home/mikhail/PychramProjects/MoodDairy/backend/core/cache.py:37), [docker-compose.yml](/home/mikhail/PychramProjects/MoodDairy/docker-compose.yml). Воспроизведено на Redis.

Версия при отсутствии создаётся как 1. Старый ответ v1 ещё может жить сутки. После удаления ключа версии ответ «1 → обновление до 9 → потеря версии» снова вернул 1. В production разрешён allkeys-lru: timeout=None не защищает ключ от eviction. Аналогичен риск пропущенной инвалидации во время отказа Redis.

**Рекомендуется:** уникальная случайная generation при каждом создании/инвалидации, без повторного использования старых значений; отдельно обеспечить корректность при пропущенной инвалидации во время недоступности кеша, например версией в БД или сбросом generation после восстановления.

**Альтернатива:** хранить revision в БД и включать его в ключ кеша. Это добавляет чтение revision, но сильнее связывает кеш с реальными изменениями.

### 10. [P2, backend/cache] Относительный период кешируется без учёта движения времени

Где: [entries/services.py:50](/home/mikhail/PychramProjects/MoodDairy/backend/entries/services.py:50), [entries/views.py:73](/home/mikhail/PychramProjects/MoodDairy/backend/entries/views.py:73), [settings/base.py](/home/mikhail/PychramProjects/MoodDairy/backend/config/settings/base.py). ### 31. [P2, UI/errors] Сбой следующей страницы скрывает уже загруженную ленту
